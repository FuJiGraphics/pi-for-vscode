# pi-for-vscode 구현 규율

이 문서는 이 코드베이스에서 기능을 만들거나 고칠 때 따르는 **작업 규율**이다. 어떤 에이전트가
읽어도 따를 수 있도록 특정 AI에 종속되지 않은 형태로 쓴다. 프로젝트 전반의 정체성·규칙은
[../AGENTS.md](../AGENTS.md)를 단일 진실 출처로 삼는다. "무엇을 어디에 두는가"의 구체적인 파일
레이아웃·커맨드 추가 절차는 [vscode-extension.md](vscode-extension.md)에 있다 — **이 문서는 "어떻게
접근하는가"를 다룬다.**

## 왜 이 문서가 있나

작업에 쫓기면 흔히 세 가지가 조용히 코드베이스를 망친다: ① **기능을 한 파일에 다 때려박고**,
② **이미 있는 코드를 안 찾고 다시 구현하고**, ③ **이미 정해진 컨벤션을 무시한다.** 셋 다 피하기는
싸고 되돌리기는 비싸다. 해법은 영웅적인 게 아니라 **짓기 전에 살펴보는 것**이다. 기존 코드를 몇 분
훑는 게 가장 효과가 크다 — 나중에 치우는 게 아니라 *무엇을 쓸지 자체*를 바꾸기 때문이다.

구현에 들어가기 전 통과하는 게이트라고 보면 된다. 아래 4단계를 순서대로 밟는다.

## 작업 순서 — 코드 쓰기 전/중에 이 4단계

### 1. 살펴보기(SURVEY) — 한 줄 쓰기 전, 가장 중요

- **이미 있는 걸 찾는다.** 작업이 건드릴 타입·함수·헬퍼·패턴을 grep/glob으로 검색한다. 검색 범위가
  넓으면(여러 파일·여러 네이밍) 별도 탐색으로 분리해 본 작업 맥락을 흐리지 않게 한다.
- **어디에 속하는 코드인지 찾는다.** 이 책임을 지금 어느 모듈/파일/계층이 갖고 있나? 따라 할 가장
  가까운 기존 예시는? (예: "다른 RPC 핸들러는 어떻게 쓰여 있나", "다른 커맨드는 어떻게 등록되나")
- **3~5줄 fit 계획을 먼저 쓴다**: 무엇을 **재사용**, 무엇을 **확장**, 무엇이 **진짜 신규**, 그리고
  **각각 어디에 둘지**. 의식(儀式)이 아니라, 재사용·배치 결정을 코드가 생기기 전(=공짜일 때) 끝내려는
  것이다.
- 이 프로젝트의 재사용 대상 예: 세션 내용은 [../src/sessionStore.ts](../src/sessionStore.ts), 모델
  목록은 활성 Pi RPC `get_available_models`, 모델 전환은 `set_model { provider, modelId }`, webview↔host 메시지는
  [../src/protocol.ts](../src/protocol.ts)의 타입 유니온, 커맨드 추가는
  [vscode-extension.md](vscode-extension.md)의 "동시 갱신" 절차.

기존 집이 있는지 안 찾아보고 새 파일을 여는 자신을 발견하면, 멈추고 먼저 살핀다.

### 2. 재사용(REUSE) > 신규

- **있는 걸 확장한다.** 헬퍼·타입·패턴이 이미 80%를 한다면 그 위에 짓는다. 새 스타일·네이밍을
  들이지 말고 기존 것에 맞춘다. **정해진 패턴을 한 케이스 때문에 함부로 갈아엎지 말고** 먼저 그
  패턴을 손본다.
- **일원화는 "지식"의 중복만 합친다** — 항상 같이 바뀌어야 하는 상수·규칙·스키마·설정. 단지
  *비슷해 보인다*고 두 코드를 병합하지 않는다. 서로 다른 이유로 바뀌는 코드를 합치면 무관한 것들을
  묶게 되고, 그게 바로 일원화가 경계하는 일이다.
- **틀린-추상화 STOP 신호:** 새 호출자를 받으려고 공용 헬퍼에 boolean/모드 플래그 + `if` 분기를
  더해야 한다면 멈춘다 — 그 호출자용으로 작은 복사본을 따로 둔다. *중복이 틀린 추상화보다 싸다.*

### 3. 제자리에 두기(PLACE) — god file 안 키우기

- **바뀔 이유 하나.** 기존 파일/클래스에 덧붙이기 전에, 그게 지금 가진 책임들을 말로 꺼내 본다. 새
  코드의 바뀔 이유가 기존 어느 것과도 다르면, 그건 새 단위에 속한다 — 여기 볼트로 붙이지 않는다.
- **god file 신호:** "and" 없이는, 혹은 모호한 `Manager/Helper/Util` 접미사 없이는 단위 이름을 못
  짓는다 / 모든 변경이 자꾸 같은 파일에 떨어진다 / 한 부분을 테스트하려면 무관한 부분의 셋업이
  필요하다. 하나라도 울리면 지금 건드리는 부분을 떼어낸다.
- **계층에 맞게 보낸다.** 관심사를 섞지 않는다 — 표현 계층이 쿼리를 만들지 말고, 데이터 계층이
  비즈니스 규칙을 품지 않는다. 지금 편집 중인 함수가 이미 계층 경계를 넘고 있으면, 새 로직을
  그게 속한 계층으로 보낸다. (구체 배치는 [vscode-extension.md](vscode-extension.md) 파일 레이아웃.)

### 4. 확장성 적정선

확장성은 *나중에 바꾸기 쉬움*이고, 응집·낮은 결합·좁은 인터페이스로 얻는다. **아무도 요청 안 한
미래를 위한 기계 장치가 아니다.**

- **지금 짓는다:** 명확한 이름, 작은 함수, 깔끔한 인터페이스 경계, 지식 중복 0. 이게 말랑함이고,
  싸며, 그 자체가 확장성이다.
- **지금 짓지 않는다:** 안 쓰는 설정 손잡이, 잠자는 훅, 아무도 안 부르는 제네릭 전략/플러그인 계층,
  현재 호출자가 안 넘기는 파라미터. 가상의 내일을 위해 오늘 복잡도를 늘리는 것들이다.
- **판정:** *지금 복잡도를 늘리나, 그리고 실제 현재 소비자가 있나?* 소비자 없음 + 복잡도 증가 →
  넣지 않는다. 추상화는 상상이 아니라 실제 반복에서 얻는다.
- **실제 사례:** broker 상태를 상태바에 표시할 때, "혹시 조용히 죽을까봐" 5초 폴링 타이머(setInterval)를
  새로 다는 것은 과잉이다 — broker가 죽으면 기존 `PiRpcClient.onClose`가 이미 울리므로, 그 신호로
  충분하다. 새 메커니즘을 더하지 말고 있는 신호를 쓴다.

## 끝내기 전 자가 점검

쓴 코드에 대고 각 항목을 소리 내어 확인한다:

- [ ] 쓰기 전에 코드베이스에서 기존 코드를 찾아봤다.
- [ ] 있는 걸 재사용·확장하고 그 컨벤션에 맞췄다.
- [ ] 실제 현재 소비자가 없는 투기적 추상은 더하지 않았다.
- [ ] 새 코드는 책임이 속한 자리에 있다(god file을 키우지 않았다).
- [ ] 우연한 중복을 병합하거나 플래그 범벅 공용 헬퍼를 만들지 않았다.
- [ ] `npm run compile`(= `tsc`)이 통과한다.

체크 못 하는 항목이 있으면 완료 보고 전에 고친다 — 정직하게 못 찍는 체크박스가 곧 신호다.

## 하지 말 것

- 있던 자리라는 이유로 무관한 책임들을 한 파일에 몰아넣기.
- 코드베이스가 이미 제공하는 걸 먼저 찾아보지 않고 다시 구현하기.
- 현재 어떤 호출자도 쓰지 않는 설정·플래그·추상 계층을 더하기.
- 위 자가 점검에 못 찍은 칸이 있는데 "완료"라고 보고하기.

## 언제 생략하나

오타, 상수/버전 하나 변경, 이미 완전히 파악한 파일의 한 줄 수정처럼 진짜 사소한 변경에는 전체
게이트를 생략한다. 살펴보기는 작업 크기에 비례한다 — 세 줄짜리 변경을 연구 프로젝트로 만들지 않는다.
